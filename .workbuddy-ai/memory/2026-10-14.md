## ★ 真正的病根：ACMD41 的 R3 响应没有 CRC7（提交 7e210ae）

用户反馈：`1 init cCRC`，2/3/4 全是 `-`（说明卡在识别阶段）。

- 推论过程：`tf_negotiate_speed()` 内部永远不返回错误（全失败也退回 4MHz），
  所以 cCRC 一定来自 `tf_identify()` 的某一步。
- 根因：`tf_cmd()` 对任何响应都检查 `SDIO_STA_CCRCFAIL` 并返回 TF_ERR_CMD_CRC。
  但 **R3（ACMD41 返回的 OCR）按规范根本没有 CRC7 字段**（48 位里最后 8 位是
  OCR 低位），SDIO 外设照它的"CRC"去比必然置 CCRCFAIL。ST 的 HAL 在
  `SDMMC_GetCmdResp2()` / `SDMMC_GetCmdResp3()` 里也是直接清掉这个标志。
  → 识别永远卡在 ACMD41，`TF_Init()` 返回 TF_ERR_CMD_CRC。
- 改法：`tf_cmd()` 拆成 `tf_cmd_ex(..., no_crc)`；R2（长响应）自动放宽，
  R3 用 `no_crc=1` 显式放宽（放宽后照样读 RESP1，由调用方判断内容）。
- 顺带两处：
  - `TF_ACMD41_TRIES`：`0x000FFFFF`(≈17 分钟) → `4000`(≈4 秒)，x TF_INIT_RETRY=3。
  - `TF_Init()` 失败收尾原来只清 `POWER`，`CLKCR.CLKEN` 还开着 →
    SDIO_CK 会一直在 PC12 上跑 400kHz（干扰源）。现在 DCTRL/CLKCR/POWER 一起清。

## 修 notSD（step 9 / cmd9）—— CSD v1.0 的 READ_BL_LEN 取错位域

串口日志：`result FAIL / status notSD / step 9 cmd9 / sta 00000000 / line 1157 / resp 80FF8000`。

先纠正两处**误读**（差点带偏）：
- `line 1157` 不是 CMD9 本身。核对 HEAD 版文件：1157 正好是
  `tf_identify()` 里 `if (g_tf.blockCount == 0U) { TF_MARK(__LINE__); ... }`。
  所以"CMD9 之后的容量检查"挂了，不是命令失败。
- `resp 80FF8000` 是**上一次**写的值，不是 CSD。`TF_MARK` 只记行号；
  `g_tfLastSta`/`g_tfLastResp` 只在出错分支赋值。这一路上没有命令报错
  （所以 sta=0），resp 还停在 ACMD41 的 CCRCFAIL 分支 = **OCR**：
  bit31=1(就绪)、bit30=0 → **SDSC 卡**。位段 23:15 全 1 = 电压窗全支持，
  0x80FF8000 正是标准 SD 卡 OCR。

根因：`tf_parse_csd()` v1.0 分支把 READ_BL_LEN 写成 `csd[1] & 0xF`，
取到的是 CSD bits 67:64 —— 那几位属于 **C_SIZE**（v1.0 的 C_SIZE 是 bits 73:62）。
于是"块大小"实际由 C_SIZE 的低 4 位决定，一旦 ≤ 8，`bl_size/512 == 0`
→ `blockCount = 0` → 判 notSD。**这是个看卡命的 bug**：C_SIZE 末位是 F 的卡
反而会"歪打正着"算出个离谱的大容量（比如 2GB 卡算出 64GB），
末位 ≤ 8 的卡直接变 0。

★ CSD 位域（这次核清楚了，两个版本 **C_SIZE 位置不同**，是最阴的坑）：
```
                     CSD v1.0                CSD v2.0
  CSD_STRUCTURE      bits 127:126 = 0        bits 127:126 = 1
  READ_BL_LEN        bits 83:80              bits 83:80（两版相同）
  C_SIZE             bits 73:62 (12 位)      bits 69:48 (22 位)
  C_SIZE_MULT        bits 49:47              —— 没有
```
独立验证：2GB SDSC 用 (C_SIZE+1)*2^(MULT+2)*2^BL，取 MULT=7、BL=10
→ C_SIZE+1 = 2^12 → C_SIZE = 4095 = 0xFFF，**正好卡满 12 位**，
与"v1.0 的 C_SIZE 是 12 位"吻合（也解释了 v2.0 为什么要把 C_SIZE 挪到
69:48 并扩到 22 位才能支持 >2GB）。

改法（提交 `6739b70`）：
- `bl_len` 改 `(csd[1] >> 16) & 0xF`（CSD bits 83:80）
- 版本判据改看 CSD 自己的 bits 127:126，不再只看 OCR 的 CCS 位，
  并顺手纠正 `g_tf.cardType`（cardType 决定后面用块地址还是字节地址）
- `bl_size < 512` 时按 1 个逻辑块兜底，别让 blockCount 又塌成 0
- `TF_Info` 加 `csd[4]` 存 CMD9 原始 CSD，串口报告新增 `csd : xxxxxxxx ...`
  一行 —— 下次容量不对可以直接手工解码，省一个来回

### 2) `sta 00000004` 的正确解读（我上一轮记错了位定义！）

⚠ **STM32F4 的 SDIO_STA 和 F1 排布不同**，别按印象来。CMSIS
`stm32f405xx.h` 里的实际定义：
```
bit0 CCRCFAIL  bit1 DCRCFAIL  bit2 CTIMEOUT  bit3 DTIMEOUT
bit4 TXUNDERR  bit5 RXOVERR   bit6 CMDREND   bit7 CMDSENT
bit8 DATAEND   bit9 STBITERR  bit10 DBCKEND  ...
```

所以 `sta = 0x04` 是 **CTIMEOUT**（不是 CMDREND！），`line 506` 正是

预期行为，不是故障。

### 3) 新 bug：DMA 停流竞态，块尾几个字节被丢（提交 64787a6）

症状矛盾点：`2 mbr: noMBR` 但 `3 fs: FAT16/12`。
FAT16 引导扇区结尾必须有 55AA，两者不可能同时成立；
而且 partLba 是从块 0 偏移 454 解析的、指向了真的 FAT16 卷，
说明**块 0 靠前的内容是对的，只有结尾不对**。

根因：`TF_ReadBlocks()` 的 DMA 分支等到 `SDIO DATAEND` 就立刻
`tf_dma_stop()`（往 CR 写 0）。但 **DATAEND 是按 SDIDCOUNT 归零置位的，
DCOUNT 归零只说明数据进了 SDIO 自己的 FIFO，不代表 DMA 已经写进内存**。
此刻停流会把还在跑的传输掐掉，块尾最后几个字丢掉。
MBR 的 510/511 正好是最后 2 字节 → 55AA 变成缓冲区旧值 0。

★★ **这个 bug 为什么不报错**（很重要，以后写 SDIO/DMA 都要防）：
- DMA 模式下 `remaining` 被无条件置 0 → 长度检查形同虚设；
- 数据 CRC 是硬件按"进了 FIFO 的字节"算的 → 照样通过；
- 反复读同一块每次都丢同样多 → 一致性测试也发现不了。
表现就是"块尾是缓冲区里的旧数据"。

修法：新增 `tf_dma_wait_done(mem_to_periph, to_ms)` —— 轮询 DMA 流的
`NDTR` 直到归零（带超时）。读/写两条 DMA 路径都在 `tf_dma_stop()`
**之前**等它走完；没走完就报 `TF_ERR_DATA_TIMEOUT` 并补 CMD12。

★ 通用结论：**SDIO(DMA) 的数据传输，DATAEND ≠ DMA 完成**。
  `DATAEND` 只保证数据进了控制器 FIFO；要保证进内存必须再等 `NDTR==0`
  （或 DMA 的 TCIF）。

### 4) 诊断增强

## 第三轮硬件反馈：确认了 DMA 真正的坑 = FIFO 残余（提交 b0e6c05）

用户日志：
```
result : FAIL / fail 1 item 2 / status dTO / step 15 read
1 init : OK
2 mbr  : dTO
type   : SDSC / blocks : 3899392
bus/clk: 4bit 4 MHz DMA HS        <-- 掉到最低档（每次读都失败）
raw    : sta 00202540 line 1605 resp 80FF8000
partlba: 0
blk0tail: 00 00 ... 00 (16 个 00)
```

### 解码 `sta 00202540`（按 F4 的 SDIO_STA 位定义）

```
bit6  CMDREND   1
bit8  DATAEND   1   <- 数据阶段正常结束
bit10 DBCKEND   1   <- 数据 CRC 通过！
bit13 RXACT     1
bit21 RXDAVL    1   <- DATAEND 那一刻 FIFO 里还有数据
```
`line 1605` = 我在读路径加的 `(remaining != 0U) || (dma_bad != 0U)` 检查。

### 真正的根因

上一版我加的"等 NDTR 归零"（最多 500ms）**始终等不到** —— 说明 DMA 不是慢，
是**停住了**。而 `RXDAVL=1` 说明 FIFO 里还躺着数据。

→ **SDIO 的 RX DMA 请求是按"RX FIFO 攒到 8 个字"（RXFIFOHF）发的。**
  数据阶段结束时 FIFO 里往往还剩最后几个字（不足 8 个），这个请求就
  再也不来了，NDTR 永远停在非 0 上 —— 块尾那几十个字节留在 FIFO 里被丢掉。

这**同时解释了上一轮的 `noMBR`**：MBR 的 510/511 就是块 0 的最后 2 字节。
也就是说上一版把"悄悄丢尾巴"变成了"明确报错"，方向是对的，只是修法不对。

★ 关键：`SDIO->FIFOCNT`（offset 0x48，只读）能直接读出 FIFO 里的字数，
  用它和 `NDTR` 对账就能**自证**残余到底在不在 FIFO 里，不用猜。

### 修法

`tf_dma_wait_done()` → `tf_dma_stop_and_drain()`：
1. 停流（CR=0，等 EN 清零，清标志）
2. 读 `NDTR`（DMA 说还剩几个 32 位字）和 `FIFOCNT`（FIFO 实际几个字）
3. `NDTR == 0` → DMA 搬完了，直接返回
4. `NDTR > 总字数` 或 `FIFOCNT < NDTR` → **说不通，报 TF_ERR_DATA_TIMEOUT**
   （宁可报错也不瞎填 —— 填错比丢掉更难查）
5. 否则：FIFO 前端若多出 `FIFOCNT - NDTR` 个字先读掉丢弃，再把最后
   `NDTR` 个字按顺序补到缓冲区末尾

写方向恢复原样（FIFO 是 DMA 灌给 SDIO 的，DATAEND 时 DMA 必然已喂完，
不存在"残余"，不引入未经验证的新失败路径）。

新增诊断：`g_tfDmaLeft`（残余字数）/ `g_tfDmaFifo`（FIFOCNT）/
`g_tfDmaIsr`（停流前 DMA2->LISR），串口报告新增 `dmadbg` 一行。

### ★★ 这次最大的收获：CubeMX 生成的 DMA 配置暴露了我们驱动的问题

新工程 `sdio.c` 里 `HAL_SD_MspInit()` 的 SDIO DMA 配置（**ST 的参考配置**）：
```c
hdma_sdio_rx.Init.Mode          = DMA_PFCTRL;              // ★ 外设做流控制器
hdma_sdio_rx.Init.FIFOMode      = DMA_FIFOMODE_ENABLE;
hdma_sdio_rx.Init.FIFOThreshold = DMA_FIFO_THRESHOLD_FULL;
hdma_sdio_rx.Init.MemBurst      = DMA_MBURST_INC4;
hdma_sdio_rx.Init.PeriphBurst   = DMA_PBURST_INC4;
```
对照我们 `tf_card.c` 的 `tf_dma_start()`：
```c
stream->FCR = DMA_SxFCR_DMDIS;                       // 只有 FIFO 使能，阈值是 1/4
cr = CHSEL | PL | MSIZE_1 | PSIZE_1 | MINC | DIR;    // ★ 没有 PFCTRL，没有 burst
```
→ **`PFCTRL`（外设流控制）正是缺的那一块**。这跟 b0e6c05 查出来的
  "SDIO 只在 FIFO 攒够 8 个字才发 DMA 请求、最后不足 8 个字永远取不走"
  完全对得上：PFCTRL=0 时由 DMA 按 NDTR 控制、请求受 FIFO 阈值门控；
  PFCTRL=1 时由 SDIO 自己决定要多少，会把尾巴也拉走。
  **这是一个还没验证的高价值猜想** —— 如果验证通过，寄存器版驱动也能跑通，
  不一定要迁移到 HAL_SD。（已向用户提出，等回复。）

### 关键实现点（都是查了 HAL 源码才敢写）

1. `TF_Init()` = `HAL_SD_Init()` + `HAL_SD_ConfigWideBusOperation(4B)`。
   - `HAL_SD_Init()` **一口气把识别全做完**（CMD0→…→CMD16），
     结果在 `hsd.SdCard`（CardType/CardVersion/RelCardAdd/LogBlockNbr/…）。
     → **`g_tfStep` 粒度变粗**：识别阶段只能标到 `CLK_INIT`。
   - ★ **`CSD[4]` 在 `SD_HandleTypeDef` 里（`hsd.CSD`），不在 `hsd.SdCard` 里** ——
     一开始写成 `c->CSD[0]` 编译报错才发现。
   - ★ 本驱动**不走 `MX_SDIO_SD_Init()`**：那个函数失败会直接 `Error_Handler()`
     停机，而驱动要能优雅返回错误码给测试台显示。
2. 读写：`HAL_SD_ReadBlocks/WriteBlocks`（**阻塞轮询**）vs
   `HAL_SD_ReadBlocks_DMA/WriteBlocks_DMA`（**异步**，靠 SDIO+DMA2 中断收尾）。
   用 `TF_USE_HAL_DMA` 切换（默认 1）。
   异步版返回后要轮询 `hsd.State != HAL_SD_STATE_BUSY` 等收尾
   （`SD_DMAReceiveCplt()` 会把 State 置回 READY，已核对源码）。
   ★ 出问题先切 `TF_USE_HAL_DMA 0` 隔离"DMA 问题"和"HAL_SD 问题"。
3. 速度：**HAL_SD 没有运行时改时钟的 API**，只能直接改 `SDIO->CLKCR` 的 CLKDIV，
   ★ 必须**保留 WIDBUS/NEGEDGE/PWRSAV/CLKEN 位**，否则会把 4 位总线配置清掉。
4. ★ **本版不做 CMD6 高速模式切换**（HAL_SD 没有对应 API）→ 最高 24MHz
   （Default Speed 上限 25MHz，不切模式跑 48MHz 不合规范），
   `highSpeedMode` 恒为 0、报告里 HS 显示 `--`，`TF_SetSpeed(48M)` 按 24M 处理。
5. 失败恢复统一用 `HAL_SD_Abort()`（等价于旧版的补 CMD12）。
6. **`g_tfLastSta` 的含义变了**：从 `SDIO->STA` 变成 **`hsd.ErrorCode`**
   （HAL_SD 的错误位），已在头文件注明。`g_tfLastResp` 仍是 `SDIO->RESP1`（直读寄存器）。
7. `g_tfDmaLeft/Fifo/Isr` 三个诊断量保留但**不再使用**（HAL 管 DMA，没有残余补数这回事）。
8. 关掉旧的日志轮播：`TF_INCLUDE_TEST` 改成 **0**（`TF_Test`/`TF_ShowLog`/
   `TF_ShowLastPage`/`TF_LogLines`/`TF_LogLine` 都没重写，测试统一走 test.c）。
